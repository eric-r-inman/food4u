=docs/compliance.org=, not this document.  Two things drive the findings:

1. *The structural checker*, run against this project from the template

2. *The template diff* across the sync window, which bounds everything the
   checker cannot express as a static rule.  A green checker run is necessary,
   not sufficient.

** The two pin failures are one problem

The lockfiles disagree with each other and both trail the template.  The Cargo
side names a later revision than the Nix side, so a Rust build and a Nix build
currently compile against different foundation versions.  Bringing both to the
template's current ~HEAD~ resolves both checks at once.

** The Apple-SDK failures are blocked on the pins

This is the one real ordering constraint in the plan, and it is easy to miss.

The template now wires the Apple SDK through a ~foundation.lib.pkgsUnfreeFor~
helper, gated behind an ~apple-frameworks~ flag in the provenance file.  That
helper *did not exist* at the revision this project's Nix input pins — it
arrived partway through the sync window.  Wiring the flake before bumping the
Nix input therefore cannot work: the attribute is simply absent.

The wiring is genuinely required rather than optional here, because the server
enables the foundation ~auth~ feature, whose TLS stack links the ~Security~,
~SystemConfiguration~, and ~CoreFoundation~ frameworks.  The flake's present
comment — asserting that the server links no Apple frameworks — is stale on that
point and should be corrected as part of the same change.

** The cosmetic failure is a hand-port artifact

Emission rewrites the template's name throughout, so a freshly emitted project
would name itself in the dev-shell marker comment.  This project's copy still
names the template, which means the comment arrived through an earlier manual
port that bypassed the substitution.  Rewording the comment clears it.

* Flows in automatically — no action

Most of the window needs no porting at all.  The reusable workflows are

* Standing opt-outs — reconfirmed

Three Windows-related checks are deliberately ignored, on the grounds that the
foundation's cross helper re-filters sources in a way that drops the SQL seed
the server embeds at compile time, and that a hosted Linux service ships no
Windows binary regardless.

That reasoning was re-verified against the updated template and *still holds*:
the Windows cross helper continues to rebuild its source set through crane's
default Cargo filter rather than honouring the caller's, so the embedded seed
would still be dropped.  The opt-outs should stay, and the note pointing at the
prior plan document remains accurate.

* Upstream observations

These belong against the template, not this project, and are recorded here only
so they are not rediscovered.

1. *Two propagated changes ship without a check.* The template's own compliance
   documentation states that a change existing projects should adopt is not
   finished until a check covers it, because a sync is driven by what the
   checker flags.  The Stop-hook clippy gate and its ~llms.org~ counterpart have
   no check, so they reach only newly emitted projects.  This review caught them
   from the diff; a checker-driven sync would not have.
2. *The pins-current check is brittle off-Linux.* It shells out to ~git~ and
   treats a warning on standard error as failure, so it errors rather than
   reports on a machine whose ~git~ emits one.
3. *The spawn registry has drifted from reality.* Most recorded project
   directories, including this one's, point at a home directory that no longer
   exists, so the checker cannot resolve them without an override.

* Refactor plan

Six phases, ordered so that nothing depends on work that has not landed.  Each
is one pull request carrying its own changelog entry, per the project's
conventions.  Phases 1, 2, and 5 are independent and may land in any order or in
parallel; phase 4 must follow phase 3; phase 6 must come last.

** Phase 1 — Convention documentation

Adopt the control-flow convention with its ~?~ carve-out, the clippy-before-
review instruction, and the restructured changelog conventions with their
examples.  Clears two checker failures and three diff-only gaps.

Pure prose, no build surface, no risk.  Largest phase by volume and the safest
to do first.  Take the template's wording rather than paraphrasing, so future
diffs stay clean.

** Phase 2 — Agent configuration

Turn off auto-memory, add the paragraph explaining why, and port the Stop hook's
clippy gate.  Clears one checker failure and two diff-only gaps.

The hook change is the only executable code in the phase.  It carries its own
round-bounding escape valve and steps aside when no toolchain is reachable, so
port it verbatim rather than adapting it.  Worth exercising deliberately: it
will gate subsequent phases' own Rust work, and phase 3 is the first to test
that.

** Phase 3 — Foundation pin realignment

Bring both lockfiles to the template's current ~HEAD~.  Clears two checker
failures and unblocks phase 4.

This is the highest-risk phase and the one to schedule attention for.  It moves
the foundation across eighteen releases, so it is the phase most likely to
require code changes rather than only lockfile edits.  The two pins currently
disagree, so this reconciles a real inconsistency rather than merely advancing a
version.  Do not fold any other phase into it — an unrelated failure here should
not be entangled with a prose change.

** Phase 4 — Apple frameworks wiring

Hoist the overlay set so the quarantined package instance stays
overlay-consistent, read the ~apple-frameworks~ opt-in from the provenance file,
pass the resulting SDK into the darwin cross helper, set the flag true, correct
the stale comment claiming the server links no Apple frameworks, and adopt the
reworked documentation.  Clears two checker failures and one diff-only gap.

*Blocked on phase 3* — the helper this depends on does not exist at the
currently pinned revision.

** Phase 5 — Cosmetic literal

Reword the dev-shell marker comment to name this project.  Clears one checker
failure.  Trivial and independent.

** Phase 6 — Provenance

Append the template's current ~HEAD~ to ~template_sync_hashes~ so the next pass
has a clean baseline, and re-examine whether the three Windows opt-out reasons
still need their pointer to the prior plan document.

Last, and only once every other phase has landed — recording the sync before the
work is complete would make the next diff-based pass silently skip whatever was
left.

* Verification

Each phase ends with the workspace build and test suite passing through the dev
shell, and with a re-run of the structural checker showing that phase's checks
cleared and nothing regressed.  Phase 3 additionally warrants a deliberate
cross-build check, since a foundation move of that size is where a packaging
regression would surface.

Reproducing the checker needs the two workarounds described [[*A caveat on reproducing the checker run][in the caveat above]];
without them, four checks error instead of reporting and the run looks worse
than it is.

** Outcome

The checker went from eight failures to none: 143 pass, 0 fail, 12 skipped as
inapplicable, and the 3 standing opt-outs.  The workspace builds, the full suite
passes, and clippy is clean under the same ~--deny warnings~ gate CI enforces.
The darwin cross-build reports its Apple SDK genuinely wired rather than merely
flagged, which is the marker the template added to tell those two states apart.

One environmental snag surfaced during verification and is worth knowing,
because it looks like a code failure and is not.  Building dev-dependencies —
which a plain build skips but the test suite and clippy do not — failed until
the tracked executables were restored to the mode git records for them.  A
checkout had narrowed them so only the owner kept the execute bit, and the
pre-commit hook's installer requires the full triad.  Nothing in the repository
was wrong; the working copy's file modes were.

* What this review deliberately leaves alone

Compliance is plumbing.  Application behaviour, domain types, route handlers,
the relational store's schema, and this project's own configuration fields are
not compliance items and are untouched by every phase above.  Where the project
diverges from the template because it is a real application rather than a
skeleton, that divergence is correct and is not recorded as a gap.
